# Phase 03: Conversational intake — Requirements

Supersedes Phase 2 R9 (the scripted dialog) and the Phase 2 decisions "Questions: prewritten per item; the LLM only extracts" and "`next` / `done`". Every other Phase 2 requirement (guard, quarantine, sources, merge rule, filter file, `/show-profile`, headless `--source`) stays in force unless a requirement below changes it.

## Functional
- R1: `/add-information` in chat (still not agent-callable) is one free conversation with the intake agent (T4). There is no sources prompt, no introduction prompt and no prewritten question. The agent opens the round with a message based on the checklist status (R3), then every user message may mix facts about the user with file paths and URLs. The agent decides what to ask next and when the round is finished.
- R2: The agent asks for missing must-know items first, then partial items (holes), then missing nice-to-have items, in the R12 order of Phase 2 within each group, and it ends the round with its `finish` tool when nothing worth asking is left or the user wants to stop. These priorities are given to the agent in its prompt and status; they are guidance to the model, not code-enforced ordering.
- R3: Each checklist item (Phase 2 R12, all twelve ids) has a stored status in `<workspace>/profile/checklist.json`: a state `missing`, `partial` or `known`, an optional short note on what is still missing (the hole), the list of origins it was learned from, and the update time. An origin is one of `conversation`, `file:<slug>`, `web:<slug>`, `hand_edit` or `profile` (already in `profile.md` when status tracking started).
- R4: The status is reconciled with `profile.md` and the manifest every time it is read: an item whose section is empty (for the CV item: no source flagged `cv`) is `missing`, whatever the file says; a filled item with no stored status, or stored as `missing`, becomes `known` with origin `hand_edit`; a stored `partial` or `known` with a filled section is kept. A missing `checklist.json` (the normal upgrade from Phase 2) is built silently: filled items become `known` with origin `profile`, empty ones `missing`, and no note is shown. An unreadable or invalid `checklist.json` is rebuilt the same way with a note in the summary (and in `/show-profile`); it never ends the round. `profile.md` stays the source of truth for content; `checklist.json` only adds state, holes and origins.
- R5: Paths and URLs in any user message are detected in code before the agent sees the message (T6): `http(s)://` URLs, `www.` hosts (read as `https://`), and tokens ending in `.txt`, `.md`, `.pdf`, `.html` or `.htm` (case-insensitive; absolute, `~/`, `./`/`../` or bare relative to the current directory; a path containing spaces only when quoted). A bare relative word such as `README.md` counts only when that file exists; otherwise it is plain text. Each detected source is ingested at once through the Phase 2 sources module (same caps, same guard, same manifest and dedupe), then read by the source reader (R7), and the outcome is reported in chat in one line per source (for example "added cv.pdf; filled skills, education"). An explicit path (absolute, `~/`, `./`, `../` or quoted) that does not exist is reported as not found and passed to the agent as such, so it can ask the user where the file is or search for it (R18). The whole message, including the source tokens, goes to the agent as the user's message.
- R6: The agent can also ingest a source the detector missed (for example "firma.cz/kariera" or "cv.pdf in my Downloads") through its `ingest_source` tool (T4). The tool accepts a URL only if it appears in a user message of this round (compared without its scheme, T7), and an `http://` URL only if the user typed it with `http://` (a URL typed with `https://`, `www.` or bare is never fetched over plain HTTP); a path without asking only if it resolves (after `~` and current-directory resolution) to a path the user typed, or the detector found, in a user message of this round; a path that matches only by its file name (names inside URL tokens do not count) or a path `find_files` returned this round (R18) only after the user confirms it in a yes/no prompt run by code that shows the full path (default no). Anything else is refused with a reason the agent sees. A spec given without a scheme that matches a bare `host/path` token the user typed (`firma.cz/kariera`) is read as `https://` + spec, unless it is path-like or a path the detector found (T7). Ingestion then runs exactly as in R5. `ingest_source(..., cv=true)`, also on a source already in the manifest (`skipped_duplicate`), flags it as the CV; the manifest's `cv` flag is written when the round is saved (R12), so a cancelled round leaves it unset.
- R7: Source texts never reach the intake agent. Every source (detected, given through `ingest_source`, dropped in, or left unextracted by an earlier round) is guarded where Phase 2 requires it, then read by the toolless extraction call (Phase 2 T8), which returns the item values and, per value, an optional hole note. Only the outcome reaches the agent: the source's origin, its status (`added`, `skipped_duplicate`, `quarantined`, `refused_no_classifier`, `error` with reason), the item ids it filled, added to or conflicted with, and the resulting checklist status. Quarantined content reaches neither model.
- R8: The agent records what the user tells it with `record_item` (T4). A recorded value from the conversation is a direct answer in the Phase 2 R13 sense: with `mode=replace` it replaces the item, with `mode=append` it is appended as a new paragraph; either way it settles the conflicts raised on that item before it. Values from sources keep the Phase 2 fill-only rule (match / adds / contradicts, conflicts reported), applied against the item as it is at that point of the round: a source read after an answer adds to the answer or conflicts with it, and that conflict stays in the summary unless a later answer settles it. Every value the app writes passes `profile.safe_body` (Phase 2 R13). `record_item` cannot write the CV item; the CV item is satisfied by a source flagged `cv` (by the reader's `is_cv`, or by `ingest_source(..., cv=true)` when the user says the file is their CV).
- R9: The agent sets an item's state and hole note with `mark_status` (`partial` with a note, or `known`). The source reader sets `partial` with its hole note when it returns one for a value it filled. A `record_item` without a later `mark_status` in the same turn leaves the item `known` and clears its note. `missing` cannot be set by a tool; it follows from an empty section (R4).
- R10: Typing exactly `done` (cs also `hotovo`), ignoring case and surrounding whitespace, or pressing Ctrl-D, ends the round at once in code without a model call, and the round is saved as if the agent had called `finish`. Ctrl-C cancels the round as in Phase 2 (`profile.md` and `checklist.json` unchanged, copied sources stay unextracted). `next` and its Czech variants are no longer special words.
- R11: Agent failure: when a turn fails (model error after the Phase 2 transient retries, a turn that gave no text and made no tool call, or a tool call with invalid arguments after one retry with the validation error fed back), the cap prints the text the agent gave earlier in the turn, if any, then a short localized error and waits for the next user message; nothing recorded so far is lost. After 3 failed turns in a row the round ends and is saved, with a note in the summary. There is no fallback to prewritten questions.
- R12: The round ends with the Phase 2 summary (R15) extended by the checklist status: items filled or changed, items still missing, partial items with their hole notes, conflicts, sources, notes, and the path of every profile file including `checklist.json`. `profile.md`, `checklist.json` and the manifest's `extracted` flags are written only at the end of the round (the Phase 2 cancel guarantee); `checklist.json` is written whenever the reconciled status differs from the stored file (so a round with only `mark_status` calls, or a first round after the upgrade, persists it), even when `profile.md` is not rewritten; then the filter file is regenerated as in Phase 2 R14.
- R13: Headless (`sortingcap run add-information [--source …]`) and `/add-information --source …` in chat run no agent, as in Phase 2 R16: sources, drop-ins and unextracted sources are read by the source reader, the profile is filled, and `checklist.json` is updated (origins and hole notes from the reader). Exit codes are unchanged.
- R14: `/show-profile` (still agent-callable and headless) also shows each item's state (`missing`, `partial` with its hole note, `known`) and its origins, reading `checklist.json` with the reconciliation of R4 (never writing it), and lists `checklist.json` among the files. It still reads no source text and no quarantine.
- R15: The agent's conversation exists only for the round: nothing of it is written to the workspace, the REPL history or the chat agent's history. The next round starts from `profile.md`, `checklist.json` and the manifest.
- R16: All new user-facing texts and the intake agent prompt exist in Czech and English; the agent writes in the user's language setting. The tour's "next steps", the chat system prompt and `/help` describe `/add-information` as a conversation. The Phase 2 keys that only served the scripted dialog (`intake.ask.*`, `intake.words.next`, `profile.item.<id>.question`, `intake.origin.intro`, `intake.origin.answer`, `intake.note.model_error_intro`, `intake.note.model_error_answer`) are removed, along with any code that reads them. New keys include a short "go on" line shown when a turn ends at its tool-call cap without text (T4).
- R17: Phase 2 maintainability follow-ups (backlog `2026-11-19-phase2-maintainability.md`), with no behaviour change: D14 (`escape_controls` and the shared `say()` helper move to `app/messages.py`), D18 (top-level imports in `app/intake/filter_file.py`), D20 (resolved by the graph rewrite, T3), D21 (`item_title` / `item_body` helpers shared by `app/intake/profile.py` and `app/tools/show_profile.py`), D22 (a configurable `FakeScorer` in `tests/helpers.py`, the `fresh_cache`, `cwd` and `en` fixtures in `tests/conftest.py`).
- R18: The agent can search for files with `find_files(name, folder=None)` (T4, T11) when the user refers to a file vaguely ("my CV in Downloads"). It returns at most 20 paths of supported-type files whose name contains `name` (case- and diacritics-insensitive), searched in `folder` when given (resolved like a path; it must exist, must be a folder the user typed this round or one of the default roots, by the T7 path rule without file-name matches, and is never a dot directory) or else in the current directory, `~`, `~/Downloads`, `~/Documents` and `~/Desktop`. The agent shows the candidates to the user; ingesting one goes through the confirmation of R6. `find_files` reads only directory listings, never file contents, and never searches inside the workspace's `quarantine/`.

## Technical
- T1: mypy as a dev dependency (latest stable, pinned in `uv.lock`), configured in `pyproject.toml` under `[tool.mypy]`: `python_version = "3.12"`, `plugins = ["pydantic.mypy"]`, `check_untyped_defs = true`, `warn_unused_ignores = true`, `warn_redundant_casts = true`; missing stubs of third-party packages handled per module in `[[tool.mypy.overrides]]` with `ignore_missing_imports`, never globally. `uv run mypy app` reports no errors; the errors found on 2026-11-19 (57 at spec time, 36 with mypy 2.4.1 after Group 1) are fixed in code, not silenced, and any remaining `# type: ignore` names its error code and carries a one-line reason. CI runs `uv run mypy app` after ruff. Tests are not type-checked in this phase.
- T2: `checklist.json` schema (Pydantic, in `app/schemas/`): `{"version": 1, "items": {<item id>: {"state": "missing"|"partial"|"known", "note": str|null, "origins": [str], "updated_at": ISO-8601 UTC}}}`. Origins are deduplicated, in first-seen order. Written through `app/files.write_private` (0600, atomic) in the same node that writes `profile.md`, after it. The reconciliation (R4) is a pure function over `ProfileDoc`, `Manifest` and the stored status.
- T3: The intake round stays a LangGraph `StateGraph` with `interrupt()` and `InMemorySaver` (Phase 2 T10), rebuilt for the conversation: `start` (load profile and status, scan drop-ins, read unextracted sources) → `agent` (one agent turn) → `listen` (interrupt for the user message) → `intake_message` (`done` check, detection, ingestion and reading) → `agent` … → `write` → `filter`; headless `start` → `write` → `filter`. Node functions live in a small class or module-level functions taking a context object, not one large closure (D20); the two identical edge functions of Phase 2 are gone; summary notes are built through one helper usable on `RoundResult`. The state stays plain JSON (Phase 2 T10). `run_round` keeps its signature and its Ctrl-C/Ctrl-D handling moves to R10's rule.
- T4: The intake agent is the chat model from settings (`ToolContext.model_factory`, as Phase 2 T10) with `bind_tools` over exactly five in-round LangChain tools with Pydantic argument schemas, every field carrying `Field(description=…)`: `record_item(item_id, text, mode="replace"|"append")`, `mark_status(item_id, state="partial"|"known", note=None)`, `ingest_source(spec, cv=False)`, `find_files(name, folder=None)`, `finish()`. These are not registry tools: the chat agent's tool list stays exactly `help`, `tour`, `show-profile` (Phase 2 T11), and the intake agent never gets a registry tool. One turn is a bounded loop: the model is called, its tool calls are executed in order and their results fed back as tool messages, until it replies with text and no tool call, calls `finish`, or reaches 8 tool calls in the turn (then the turn ends with whatever text it gave, or the localized "go on" line when it gave none; it does not count as a failure; nothing is logged). The text reply is printed to the user as plain text (no Markdown or Rich markup rendering, controls escaped).
- T5: The agent's input per turn: the system prompt `prompts/<lang>/intake/agent.md` (read through `app/texts.py`), then the round's messages: the user's messages, the agent's replies and tool messages, and before the latest user message (or alone, in the opening turn) one context message, a user-role JSON message rebuilt each turn, with the current checklist status (id, title, state, note, origins, current value) and the reports of sources handled since the last turn (R7). The status and reports are JSON, so values written from guarded sources stay data. The round's history is capped at about the last 40 messages, cut only at user-message boundaries, so an AI message with tool calls is never separated from its tool results (the status message carries what was learned earlier); the system prompt and the latest status are always included. Each current value in the status message is cut at 1500 characters, with the cut marked.
- T6: The detector is plain code in `app/intake/detect.py`, `detect(message, cwd) -> list[Detected]` (spec as written, normalised spec (`www.` → `https://`), kind `url` or `path`, whether it is explicit (R5), position). It runs in linear time on untrusted text: no overlapping unbounded quantifiers, tokens found by a single scan, trailing punctuation (`.,;:!?)]}>"'`) stripped from URLs and paths. A performance test runs it on adversarial input (a 1 MiB message of repeated `http://`, dots, slashes, quotes and extensions) within a few seconds. At most 10 sources per message are ingested; further ones are reported as skipped for the turn.
- T7: The `ingest_source` allow rule (R6) is a pure function over the spec, the round's user messages, the paths the detector found in them and the round's `find_files` results: URLs compared without scheme (an `http://` spec only matches a URL typed with `http://`; one typed with `http://` also allows `https://`), after stripping trailing punctuation and a trailing `/`, against the URLs (typed with a scheme or `www.`) and bare host/path tokens (containing a dot) of the user messages; a bare token counts only if its host is a name, not an address: its last label contains a letter and is no `0x` number, and the host is no IPv4 or IPv6 literal in any form (`10.1`, `127.1`, `0x7f.1`, `127.0.0.1`, `[::1]`); a URL allowed only through a bare token is flagged in the verdict, and its fetch refuses a local or private host (loopback, private, link-local), while a URL typed with a scheme may be local; a spec without a scheme that matches a bare token is read as `https://` + spec and flagged the same way, unless it is path-like (`/`, `~`, `./`, `../`), its first segment has no dot, it is a bare file name of a supported type, or it resolves to a detected path; the URL to ingest is returned with trailing punctuation removed; paths resolved lexically (`~` expanded against the home folder, relative paths joined to the current directory, empty and `.` segments dropped, `..` kept since it may cross a symlink) and allowed when equal to a resolved token (other than a URL token) or detected path of the user messages; a match by file name only (`Path(spec).name`, case-sensitive, against the tokens that are not URLs: not with a scheme, not `www.`, not a bare `host/path` link) or a `find_files` result is allowed only with the confirmation of R6, and the verdict carries the resolved full path. `find_files` folders go through the same path rule (`allow_folder`), without file-name matches, with the default roots of T11 also allowed. The verdict (allowed / allowed after confirmation / refused) is decided before any file read or fetch.
- T8: The extraction output (`ExtractedValue`, Phase 2 T8) gains `gap: str | None` with a `Field(description=…)`: what is still missing for this item after this text (for example "no currency"), null when the value looks complete. It goes through `invoke_structured` as before. The extraction prompt (`prompts/<lang>/intake/extract.md`) explains `gap`; the `question` input field is removed, as there are no questions to answer.
- T9: Tests run offline with fake models: a scripted tool-calling fake (the Phase 1 `FakeToolModel`, extended if needed so a script can return tool calls and texts per call and record the messages it was given) drives full rounds; the structured fake drives the reader. No real model, no network.
- T11: `find_files` is plain code in `app/intake/find.py`: it walks at most 3 directory levels below each root, skips dot directories and symlinked directories, stops after 5000 directory entries per call, lists only `.txt`, `.md`, `.pdf`, `.html` and `.htm` files, and returns absolute paths sorted by most recent modification, at most 20. Without a `folder` the roots are walked in the order current directory, `~/Downloads`, `~/Documents`, `~/Desktop`, `~`, each directory once. A `folder` the user did not type this round (T7) gives `folder_not_typed` before anything is read; a `folder` that is or lies in a dot directory (also through `..` or a symlink) gives `hidden_folder`; one that does not exist or is not a directory gives `not_found` / `not_a_directory`; every error is a result the agent sees. Results are recorded in the round state for T7. File names are shown with controls escaped.
- T10: Constitution amendments (same branch): tech-stack Architecture "LLM calls belong only in …" adds the intake agent; a new line records that the intake agent has in-round tools only and never sees source text (source texts go only to the toolless extraction call); tech-stack Quality tooling drops "added in phase 3. Until then the rule above applies to ruff and tests only" and states CI runs mypy; tech-stack Project structure mentions `app/intake/` holding the intake agent.

## Out of scope
- Keeping or replaying conversation transcripts across rounds.
- Prewritten questions or a guided mode of any kind.
- Type-checking `tests/`; mypy `--strict`.
- The intake agent reading source texts, or any registry tool.
- New source formats; vector index; changes to the guard, quarantine or filter-file rules.
- Making `/add-information` agent-callable.

| Phase scope | Keep all five roadmap items in one phase | Medium phases by choice | spec interview |
