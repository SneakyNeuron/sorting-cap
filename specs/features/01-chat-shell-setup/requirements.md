# Phase 01: Chat shell, tool registry and setup — Requirements

## Functional
- R1: After `git clone` and `uv sync`, `uv run sortingcap` starts the terminal chat; `uv run sortingcap --version` prints the version.
- R2: Every capability is a registered tool, and the same tool can be run as a dash-command in chat (`-name --flag value`) and headless (`sortingcap run name --flag value`), with identical arguments, validation and results. Tools marked chat-only (Phase 1: `setup`) are refused by the headless runner.
- R3: The headless runner supports `--json` (machine-readable output), `--yes` (auto-confirm) and exit codes 0 / 1 (tool failure) / 2 (bad arguments); without `--yes`, every confirmation is denied; a prompt for a choice, text or hidden input fails the run (exit 1); a chat-only tool is refused (exit 2).
- R4: In chat, a line starting with `-` runs a tool; any other text goes to the chat agent, which can call only tools marked agent-callable (Phase 1: `help`, `tour`).
- R5: `-help` lists all commands with descriptions in the current language; `-help <command>` shows that command's flags.
- R6: On the very first start (no language chosen yet) the REPL first asks for the language (cs/en, bilingual prompt) and saves it, then greets in that language. The REPL keeps history across sessions, completes dash-commands with Tab, accepts multi-line paste, survives tool and model errors, quits on `-exit` or Ctrl-D, and cancels on Ctrl-C without quitting.
- R7: The workspace defaults to `~/SortingCap`, is overridden by `SORTINGCAP_WORKSPACE`, and is created on first use with mode 0700. An existing workspace keeps its mode; when group or others have any access the REPL warns at start and shows `chmod 700 <path>`. `.history`, `settings.json` and `.env` are kept at mode 0600.
- R8: Settings (language cs/en, provider, model, Ollama URL, OpenAI-compatible base URL) live in `<workspace>/settings.json`, are re-read on every command so hand edits apply, and can be shown and changed with `-settings` (user-only). A change of provider, model, language, endpoint URL or the active provider's key (compared as a SHA-256 digest, never stored raw) rebuilds the chat agent before the next message and keeps the conversation history.
- R9: `-setup` (user-only) guides the user through language, a hardware summary and a provider menu (local Ollama preselected when the hardware fits, Novita, any OpenAI-compatible endpoint; more providers later). A remote provider is never preselected; when local is unavailable, nothing is preselected. The chosen provider is set up and verified by a chat reply plus a tool call; on failure or a declined step the user returns to the menu with the reason and can pick another route or quit. For local Ollama: detection, start or install (Docker container or native install script) after an explicit yes for each command shown (an existing `ollama` container is reused on the port it is published on, so a retry never runs a second `docker run`; a non-loopback `ollama_base_url` that does not answer as Ollama fails back to the menu with a hint to check the URL or reset it to `http://localhost:11434`, and nothing is installed or started for it), a list of every recommended Qwen tier that fits the detected hardware (T5) with the best one marked and preselected, and pull with progress. If no local tier fits, the local option is shown as unavailable with a message that the hardware is not sufficient and that Novita or other providers can run the agents instead.
- R10: Choosing a remote provider shows that prompts and data leave the machine. An OpenAI-compatible URL or an `ollama_base_url` whose host is loopback (`localhost`, `127.0.0.0/8`, `::1`) counts as local: no notice; every other host, LAN included, is remote (so `ollama` with a non-loopback `ollama_base_url` gets the notice in `-setup` before the URL is contacted, and in `-settings`). A remote URL with plain `http://` also gets a warning that prompts and any key travel unencrypted; it is still allowed (LAN servers often lack TLS). When `-setup` for the OpenAI-compatible option is given a URL whose host differs from the saved one and a key is already stored, the key prompt says that an empty answer sends the stored key to the new host. Novita asks for the key (hidden input) and lets the user pick a function-calling model from Novita's list (no default). The OpenAI-compatible option asks for a base URL, an optional key and a model name. A typed key is held in memory and used for the model list and verification; only after verification succeeds is it stored in `<workspace>/.env` with mode 0600 (written to a 0600 temporary file and atomically renamed; a value with a newline or another control character is refused), so a failed or abandoned `-setup` leaves the stored key unchanged. When the key's environment variable is set it wins over `.env`, so `-setup` says so and does not ask for a key. A remote provider is used only when the user picks it in the menu or with `-settings`; `-settings` shows the same notice and asks for confirmation before any change that makes the configured provider remote or points a remote provider at another endpoint URL, and changes nothing when declined. `ollama_base_url` and `openai_base_url` must be `http://` or `https://` URLs with a host; anything else is rejected by `Settings` validation (hand edits included).
- R11: After the first successful `-setup`, the app overview and tour are shown once; `-tour` shows them any time. The tour ends with a "next steps" section that later phases extend.
- R12: All user-facing texts exist in Czech (default) and English; prompts live in `prompts/<lang>/<agent>/`, prewritten texts and UI messages in `defaults/texts/<lang>/`.
- R13: README documents install, run, `-setup`, the commands, the headless runner (with `setup` chat-only), the workspace (including where `.env` goes) and development commands.
- R14: When the model returns reasoning ("thinking"), the chat shows it in dim text above the answer; the answer itself is rendered normally. This holds for all three Phase 1 providers.

## Technical
- T1: Python 3.12 (`requires-python = ">=3.12,<3.13"`), managed by uv; dependencies in `pyproject.toml`, exact pins in a committed `uv.lock`; CI uses `uv sync --locked`. Versions are the latest stable at implementation time and must stay within: `langchain` 1.x, `langchain-ollama`, `langchain-deepseek` (brings `langchain-openai`), `pydantic` 2.x, `prompt-toolkit` 3.x, `rich`, `httpx` (Ollama and Novita HTTP calls outside LangChain); dev: `pytest`, `pytest-socket`, `respx`, `ruff`. Build backend: `uv_build`. `.env` is read by a small built-in parser, not python-dotenv. All must be GPL-3.0-compatible.
- T2: The CLI and dash-command parser is argparse, generated from the registry's Pydantic input models; chat dash-commands are split with `shlex` and parsed by the same parser.
- T3: The chat agent is LangChain `create_agent` with a chat model built from settings: `ChatOllama` with `reasoning=True` (provider `ollama`), `ChatDeepSeek` from `langchain-deepseek` with `api_base` set to Novita's OpenAI-compatible base URL (provider `novita`), or `ChatDeepSeek` with `api_base` set to `openai_base_url` (provider `openai_compatible`; key optional, a `not-needed` placeholder is sent when empty because the OpenAI client requires one). `api_key` and `api_base` are always passed explicitly, so `ChatDeepSeek`'s fallback to `DEEPSEEK_API_KEY`/`DEEPSEEK_API_BASE` never applies. Reasoning arrives in `additional_kwargs["reasoning_content"]` for all three, so it can be shown dim (R14). `ChatOpenAI` is not used directly: in `langchain-openai` 1.x it drops non-standard fields such as `reasoning_content` (verified in due diligence 2026-11-17 against 1.8.0). No in-house LLM wrapper.
- T4: Tools carry an `agent_callable` flag; the agent's tool list is built only from flagged tools. `setup` and `settings` are not agent-callable. Tools also carry a `chat_only` flag; the headless runner refuses them. `setup` is chat-only. `ToolContext` offers `confirm()`, `choose()`, `text()` and `secret()`; headless, `confirm()` is false unless `--yes`, and the other three fail the run. `-exit` is a REPL built-in, listed in `-help` and completion but not a tool.
- T5: Local model tiers are Qwen-family tags from Ollama's library with the `tools` capability and an Apache-2.0 licence (free redistribution and use). `-setup` lists every tier that fits the detected hardware and preselects the best one by the rule below. Detected sizes are converted to GiB and rounded to the nearest whole GB before the comparison (a 24 GB card reports about 23.99 GiB, a 16 GB machine about 15.5 GiB), so nominal hardware gets its nominal tier. Sizes are Ollama download sizes, and tags, tools capability and licences were verified on 2026-11-17. VRAM/RAM minimums and speed notes are **estimates**: model size plus about 3–6 GB for context and runtime on GPU, and about 8 GB for the OS on CPU. Thinking is on by default in every listed model. No "qwen4" model exists in Ollama's library; the experimental `qwen3.8-flash-next` (125B, "Qwen4 preview", non-Apache licence) is excluded.

| # | Tag | Generation, size, type | Download | Min VRAM (GPU) | Min RAM (CPU-only) | Best pick when |
|---|---|---|---|---|---|---|
| 1 | `qwen3.5:122b-a10b-q4_K_M` | Qwen3.5, 125B MoE, 10B active | 81 GB | 96 GB | 96 GB (slow, est.) | Workstations/servers with ≥ 96 GB VRAM or RAM |
| 2 | `qwen3.8:27b-q8_0` | Qwen3.8, 27B dense | 30 GB | 40 GB | not realistic | 40–48 GB+ VRAM: newest generation at near-lossless precision |
| 3 | `qwen3.8:27b-q4_K_M` | Qwen3.8, 27B dense | 18 GB | 24 GB | not realistic | 24–32 GB VRAM: newest and strongest model that fits fully on the GPU |
| 4 | `qwen3.6:35b-a3b-q8_0` | Qwen3.6, 36B MoE, 3B active | 39 GB | 44 GB | 48 GB | CPU-only (no tier fits the GPU) with ≥ 48 GB RAM, e.g. 64 GB boxes; offered but not preselected when a smaller tier fits the GPU |
| 5 | `qwen3.6:35b-a3b-q4_K_M` | Qwen3.6, 36B MoE, 3B active | 24 GB | 28 GB | 32 GB | CPU-only (no tier fits the GPU) with 32–47 GB RAM; offered but not preselected when a smaller tier fits the GPU |
| 6 | `qwen3.5:9b-q8_0` | Qwen3.5, 9.7B dense | 10 GB | 12 GB | none (GPU only) | 12–23 GB VRAM |
| 7 | `qwen3.5:9b-q4_K_M` | Qwen3.5, 9.7B dense | 6.6 GB | 8 GB | 16 GB (slow, est.) | 8–10 GB VRAM, or CPU-only with 16–31 GB RAM |
| 8 | `qwen3.5:4b-q4_K_M` | Qwen3.5, 4.7B dense | 3.3 GB | 5 GB | 8 GB | Small GPUs (5–7 GB) or CPU-only with 8–15 GB RAM |
| 9 | `qwen3.5:2b-q4_K_M` | Qwen3.5, 2.3B dense | 1.9 GB | 3 GB | 6 GB | Floor tier for ≤ 4 GB VRAM or 6–7 GB RAM; weak tool calling, so suggest Novita alongside |

Selection rule (deterministic). `V` is the largest NVIDIA GPU's VRAM in GB (rounded as above) (0 when there is no NVIDIA GPU or no `nvidia-smi`) and `R` is total RAM (`MemTotal`) in GB, rounded as above. A tier fits when `V ≥ min VRAM` or (a CPU minimum exists and `R ≥ min RAM`); rows 2, 3 and 6 have no CPU minimum. The offered tiers are all fitting rows, ordered by expected quality (lowest `#` best). Preselection is GPU-fit first: if any row has `V ≥ min VRAM`, the preselected tier is the lowest `#` among those rows; otherwise it is the lowest `#` among rows that fit by RAM. If no row fits (`V < 3` and `R < 6`), local is unavailable (R9). Examples: no GPU, 8 GB RAM → 8; no GPU, 16 GB → 7; no GPU, 32 GB → 5; no GPU, 64 GB → 4; no GPU, 128 GB → 1; 8 GB VRAM, 16 GB RAM → 7; 12 GB VRAM, 16 GB RAM → 6; 12 GB VRAM, 64 GB RAM → 6; 16 GB VRAM, 32 GB RAM → 6; 4 GB VRAM, 64 GB RAM → 9 (4 also offered); 8 GB VRAM, 64 GB RAM → 7 (4 also offered); no GPU, 24 GB RAM → 7 (6 not offered); 24 GB VRAM, 125 GB RAM → 3; 48 GB VRAM → 2; 96 GB VRAM → 1.
- T6: Ollama endpoints used: `GET /api/version` (detection), `GET /api/tags` (installed models), `POST /api/pull` (streamed pull progress). The Docker install runs `docker run -d --name ollama -v ollama:/root/.ollama -p 127.0.0.1:11434:11434 [--gpus=all] ollama/ollama` (bound to loopback only, so the model is not reachable from the network; the port changes when 11434 is taken). Before any `docker run`, `docker container inspect --format '{{.State.Status}} {{json .HostConfig.PortBindings}}' ollama` looks for an existing container and its published host port for 11434; when one exists it is reused (`docker start ollama` if stopped) at `http://localhost:<that port>`, and when it cannot serve on a free port the user is told to remove it with `docker rm -f ollama`. A detached `ollama serve` gets `OLLAMA_HOST=<host>:<port>` from `ollama_base_url` (`localhost` → `127.0.0.1`), shown with the command; the native install runs the official script `curl -fsSL https://ollama.com/install.sh | sh`. Both are shown in full before the user confirms.
- T7: Every external command (`docker`, `curl | sh`, `systemctl`, `ollama serve`, `nvidia-smi`) runs through `app/setup/runner.py`, which can be faked, accepts extra environment variables for the command (added to the inherited environment) and logs each command line, with those variables, and exit code to `<workspace>/logs/setup.log`; no other module imports `subprocess`, and no command line carries a key.
- T8: Remote keys are read from `NOVITA_API_KEY` and `SORTINGCAP_OPENAI_API_KEY` in the environment, falling back to `<workspace>/.env`; keys are never written to `settings.json`, logs, output (shown masked) or the REPL history file; hidden key prompts bypass history.
- T9: No prompt or user-facing text inline in code: prompts are files under `prompts/`, read only through `app/texts.py`; UI strings, error texts (including settings-file, workspace and validation errors and the CLI usage line) and tool/flag help are message keys in `defaults/texts/<lang>/messages.json`. Pydantic validation problems are shown in the user's language when a `validation.<error type>` key exists (the app's own validators and the common built-in types); other types keep Pydantic's English text, as do argparse's own messages inside `parse.bad_arguments`. All tool inputs and outputs and `Settings` are Pydantic v2 models; tool input/output models live in `app/schemas/`.
- T10: Tests run offline with sockets disabled (pytest-socket): a fake chat model that supports `bind_tools`, faked command runner and HTTP, temporary home and workspace. Tests mirror the `app/` layout in `tests/`. Ruff (`E`, `F`, `I`, `B`, `UP`, `SIM`) and `ruff format --check` are clean.
- T11: CI (GitHub Actions; `actions/checkout@v7.0.1`, `astral-sh/setup-uv@68559e99cc807c1eb7e9238fd43a15bba460eec2 # v10.3.3`, which has no floating `v10` tag) runs `uv sync --locked`, `uv run ruff check`, `uv run ruff format --check` and `uv run pytest` on push and pull request.
- T12: Providers are registered in `app/providers/`; each declares availability for the detected hardware, its setup steps, verification and how to build its LangChain chat model. `-setup`'s menu and `Settings.provider` validation come from that registry.
- T13: Novita uses its OpenAI-compatible endpoint; the base URL is `https://api.novita.ai/openai/v1`, so chat goes to `<base>/chat/completions` and the model list to `<base>/models` (`GET https://api.novita.ai/openai/v1/models`). There is no default model: setup lists the models that the list marks with the `function-calling` feature and the user picks one (or types an id). The `openai_compatible` provider takes any http(s) base URL including its version path, OpenAI convention (`openai_base_url`, e.g. `http://localhost:1234/v1`; the app appends `/chat/completions` and `/models`), an optional key and a model name. For both, the model can be changed later with `-settings --model`. Ollama API references in code cite https://docs.ollama.com/api.
- T14: Packaging: `uv_build` with `app/` as the import package; `prompts/` and `defaults/` stay at the repository root and are found via `app/paths.py` (editable install from `uv sync`).
- T15: LangSmith tracing is always disabled: when `app/cli.py` is imported, before any `langchain` or `langsmith` import (langsmith caches environment lookups), one function sets `LANGSMITH_TRACING_V2`, `LANGSMITH_TRACING`, `LANGCHAIN_TRACING_V2` and `LANGCHAIN_TRACING` to `false` in its own process (langsmith 0.15 reads `TRACING_V2`, falling back to `TRACING`, in the `LANGSMITH_` then `LANGCHAIN_` namespace, so these four are every name it consults), whatever the user's environment says, and removes `LANGSMITH_GATEWAY` so no chat model is routed through the LangSmith gateway. There is no setting to enable it. (The `langsmith` package is a required dependency of `langchain-core`; it stays installed but inactive.)

## Out of scope
- Profile intake, the injection guard, scraping, listings, cron and letters (Phases 2–5).
- macOS or Windows install paths for Ollama (Linux first; macOS best effort later).
- Remote providers other than Novita and the generic OpenAI-compatible endpoint.
- An opt-in live-model test suite (first needed in Phase 3).
- Packaging for PyPI or `uv tool install`.
